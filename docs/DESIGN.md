# 설계 문서

실행 방법은 [`../README.md`](../README.md) 를 보십시오.
이 문서는 **왜 이렇게 만들었는지**를 남긴다.

이미지를 입력받아 **개인정보 영역의 좌표와 유형**을 반환한다.
마스킹/치환은 이 파이프라인의 출력을 소비하는 **별도 모듈**에서 수행한다.

```
입력: 금융 문서 이미지 1장
출력: [{"bbox": [412, 780, 690, 812], "type": "RRN", ...}, ...]
```

현재 용도는 **학습데이터 구축**이다. 따라서 정책은 **recall 최우선**이다.

---

## 왜 다시 만들었나 — 순서가 뒤집혀 있었다

첫 구조는 다섯 단계였다.

```
OCR → 규칙 레이어(정규식+체크섬) → LLM pass-1(텍스트) → VLM pass-2(이미지) → 값 전파 → 병합
```

실제 문서로 돌려본 결과가 좋지 않았고, 원인을 추적하니 **단계 순서 자체가
문제**였다.

개인정보 판단은 **의미** 문제고, 좌표는 **기하** 문제다. 그런데 저 구조는
기하(OCR)를 먼저 돌리고 그 결과를 의미 판단의 **입력 형식으로 강제**했다.
그래서 VLM 이 받은 과제는 이렇게 되었다.

1. 이미지에서 작은 한글·숫자를 읽고
2. 100줄 넘는 정규화 좌표 박스 목록을 읽고
3. "이미 탐지된 번호" 목록과 **집합 차집합을 계산**하고
4. 시각적 위치를 **박스 번호로 grounding** 해서 답한다

3번과 4번이 LLM 이 구조적으로 가장 못하는 일이다. 관측된 결과가 그대로였다.

| 관측 | 원인 |
|---|---|
| 노이즈 심한 스캔 페이지에서 **이미지 pass 기여가 0** | `"놓친 것만 찾아라"` + 이미 찾은 번호 목록이 강한 앵커. 모델이 `{"missed":[]}` 를 낸다 |
| `NAME` 박스가 **`"성 명"` 헤더 셀**에 붙고 실제 이름은 비어 있음 | 박스 번호 grounding 실패. 틀린 번호를 검증할 방법이 없다 |
| 주민등록번호가 **`DRIVER_LICENSE` conf 1.00** 으로 확정 | 정규식이 탐지기 역할을 하면서 체크섬 없는 라벨을 "통과" 로 취급 |
| 숫자 칸이 전부 `OTHER` | pass-1 의 라벨셋이 `RRN` 을 말할 수 없게 절단되어 있었다 |
| 주민등록번호 여러 개가 **아무 박스도 못 받음** | OCR rec 실패 → 규칙·pass-1·pass-2 모두 회수 실패 |

그리고 **오차를 어느 단계에 귀속시킬 수 없었다.** 단계 간 계약이 다섯 개
(`<CONFIRMED>` 태그, 라벨셋 분리, `(박스,라벨)` 원장, 전파 씨앗, 병합 우선순위)
였고, 위 버그들은 대부분 그 계약들이 만들어낸 것이었다.

**복잡도가 버그의 원인이었다.** 그래서 고치는 대신 순서를 뒤집고 단계를 줄였다.

## 파이프라인 — 두 단계

```
입력: 금융 이미지 1장  또는  PDF (페이지별로 분해)
   │
   ├─① 전처리       기울기 보정 + 해상도 정규화
   │
   ├─② VLM 탐지     이미지만 보고 개인정보를 전사한다
   │                → {"text":"901112-2846261","type":"RRN",
   │                    "field":"자녀 주민등록번호","bbox_norm":[...],"conf":0.9}
   │                판단은 신뢰, 좌표는 대략, 전사는 참고
   │
   ├─③ 크롭 OCR     ②가 지목한 곳을 잘라 배치 인식 → 정밀 좌표
   │                크롭 안에서 대상 박스를 고른다 (텍스트 일치 → 위치 겹침)
   │
   ├─④ 검증         체크섬 · 자리수 · 항목명 필터 · 중복 제거
   │
   └─⑤ 결과 JSON    bbox + type + 좌표 획득 경로
```

단계가 둘이면 **성적표가 단계에 1:1 로 대응한다.**

```
n_findings      ② 가 몇 건 찾았나        → VLM 재현율
localized_rate  ③ 이 몇 %의 좌표를 잡았나 → 기하 성능
n_disagreement  두 엔진이 다르게 읽은 건수 → 신뢰도
```

이게 재설계의 실질적 목적이다. 개선이 측정되지 않으면 개선할 수 없다.

## 핵심 설계 결정 5개

### 1. 판단과 좌표를 다른 엔진에 맡긴다

VLM 에게는 **"무엇을 읽었나"** 만 묻는다. 좌표는 "크롭할 수 있을 정도" 만 받고,
정밀 좌표는 OCR 이 정한다.

그래서 프롬프트가 **좌표 압박을 의도적으로 낮춘다.**

> `bbox_norm` — 크롭에만 쓴다. 대략이어도 된다.
> 이 좌표는 그 부분을 잘라내 OCR 에 넘기는 데만 쓰이고, **최종 좌표는 OCR 이
> 다시 정한다.** 그러니 픽셀 단위로 맞추려고 애쓰지 마라.
> 값을 정확히 읽는 것이 좌표보다 훨씬 중요하다.

좌표 정확도를 요구하면 그 용량이 전사 정확도에서 빠져나간다. 9B 모델에서는
이 트레이드오프가 실재한다.

**guided-decoding 스키마의 속성 순서도 설계 결정이다.**
`text` → `type` → `field` → `bbox_norm` 순으로 생성되게 두었다. 즉 "무엇을
읽었는지" 를 먼저 확정하고 그 다음에 "어디인지" 를 답한다. 좌표를 먼저 내게
하면 값이 좌표에 끌려간다 — 읽기보다 좌표 찍기가 어려우므로, 좌표를 먼저
고정하면 그 근처에서 값을 짜맞춘다.

### 2. VLM 에게 목록을 주고 고르라고 하지 않는다

주는 것은 이미지 하나뿐이다. OCR 박스 목록도, "이미 탐지된 번호" 도 없다.

**전사(transcription)는 VLM 이 학습된 태스크**이고, 차집합 계산과 index
grounding 은 아니다. 옛 프롬프트에 있던 `"박스 번호"`, `"이미 탐지된"`,
`"놓친 것만"`, `"idx"` 라는 문구는 `tests/test_prompts.py` 가 회귀 테스트로
금지한다 — 되돌아가면 테스트가 깨진다.

부수 효과로 프롬프트가 ~2500토큰 + 100줄 목록에서 ~900토큰으로 줄었다.
9B 모델이 실제로 이미지를 볼 예산이 생긴다.

### 3. 타일링은 선택이 아니라 필수다

한 번의 호출로 페이지 전체를 전사하게 하면 **뒤쪽 항목이 잘린다.** 모델이
분류를 못해서가 아니라 긴 구조화 출력의 후반부가 무너지기 때문이다.
가족관계증명서 한 장이 구성원 9명 × 4필드 = 36건인데, 9B 모델이 36건을 한 번에
온전히 뱉기를 기대하는 것은 무리다.

페이지를 **긴 축 방향으로** 3조각으로 나눠 조각당 한 번 호출한다. 긴 축을
자르는 것은 조각을 정사각형에 가깝게 만들기 위한 것이다 — VLM 의 비전 인코더는
극단적으로 긴 이미지에서 한쪽을 크게 줄인다.

**해상도 문제가 여기서 함께 풀린다.** 이전 구조의 실측 문제 중 하나가 이거였다.

| 설정 | VLM 이 보는 것 |
|---|---|
| 2480px 페이지 통째로, `image_max_side=1800` | 0.73배 축소 → 주민번호 숫자 ~10px. **읽을 수 없다** |
| 3조각, `image_max_side=2000` | 조각 긴 변 1748 → **축소 없음** |

`--print-config` 가 이 조합을 검산해 `"축소 없음"` / `"축소 발생"` 을 알려준다.
따로 관리하면 한쪽만 바꿔놓고 "왜 작은 글씨를 못 읽지" 로 헤매게 된다.

조각은 8% 겹쳐 자른다. 겹침이 없으면 경계에 걸친 한 줄이 양쪽에서 반씩 잘려
둘 다 못 읽는다. 겹침에서 생긴 중복은 코드가 정리하되, **값이 같아도 위치가
겹치지 않으면 남긴다** — 같은 이름이 문서 여러 곳에 나오는 것은 정상이고 각각
마스킹해야 한다.

시스템 프롬프트와 user 메시지는 **완전히 고정**이다. 타일 번호조차 넣지
않는다 (좌표 환산은 코드가 한다). vLLM prefix caching 이 이미지 앞까지 걸려야
조각 수를 늘려도 비용이 선형으로 늘지 않는다.

### 4. OCR 은 탐지기가 아니라 측량기다

무엇이 개인정보인지는 ②가 이미 판단했다. OCR 은 "그 값이 정확히 어느 픽셀에
있는가" 만 답한다. 그래서 페이지 전체가 아니라 **크롭들**을 받는다.

크롭 단위가 페이지 단위보다 유리한 이유 세 개.

1. **det 가 쉬워진다.** 밀집한 노이즈 표에서 페이지 det 는 인접 셀을 붙이거나
   한 셀을 쪼갠다. 한 칸짜리 크롭에서는 그런 모호함이 없다.
2. **업샘플이 가능하다.** 작은 크롭은 2배로 키워도 비용이 무시할 만하고, rec
   모델은 입력 글자 높이에 민감하므로 10px 글자에서 실측 효과가 있다.
3. **실패가 국소적이다.** 한 크롭의 rec 실패는 그 항목 하나만 `vlm_coarse` 로
   떨어뜨린다. 페이지 전체 판단에 영향을 주지 않는다.

### 4-1. 박스 선택 — 전사 정확도를 임계 경로에서 뺀다

이 단계에 **모델 호출은 없다.** 선택은 전부 코드가 결정론적으로 한다. 크롭 OCR
결과를 다시 VLM 에게 보여주고 고르라고 하면 이전 구조의 실패(시각적 위치를 박스
번호로 표현시키기)로 되돌아가고, 비용도 `O(타일)` 에서 `O(항목)` 으로 등급이
바뀐다 — 항목 25건이면 호출 25회, 페이지가 빽빽할수록(개인정보가 많을수록) 더
비싸지는 최악의 방향이다.

선택 순서는 **좁은 답부터, 확실한 근거부터**다.

| 순위 | 근거 | 좌표 | `agreement` |
|---|---|---|---|
| ① | 박스 1개 안에서 텍스트 완전일치 | 정확 | `exact` |
| ② | 인접 박스 이어붙여 완전일치 | 정확 | `exact` |
| ③ | **VLM bbox 와 위치가 겹치는 박스** (텍스트 안 봄) | 정확 | `none` |
| ④ | 크롭에 OCR 박스가 없음 | 근사 | `none` |

좁은 답을 먼저 찾는 이유: 이어붙이기나 기하를 먼저 시도하면 값 하나에 옆 칸이
딸려 들어와 박스가 셀 두 개를 덮는다 (이전 구조의 "컬럼을 가로지르는 길쭉한
박스" 가 이거였다).

**③이 왜 필요한가 — 이 설계에서 가장 늦게 깨달은 것이다.**

처음에는 ①②만 두고 "VLM 의 좌표는 신뢰하지 않고 VLM 의 텍스트를 신뢰한다" 를
원칙으로 삼았다. 그런데 그건 **VLM 의 가장 약한 능력을 임계 경로에 올린 것**
이었다.

VLM 이 잘하는 일은 "여기에 이 종류의 개인정보가 있다" 는 판단이다. 근거가
중복적이기 때문이다 — 필드 라벨, 표 구조상의 위치, 옆 칸과의 관계, 값의 대략적
형태. 하나만 보여도 판단이 선다.

반면 `901112-2846261` 을 13자리 모두 정확히 맞히는 것은 **중복성이 0인** 과제다.
13번의 독립적 정답이 필요하고, 오독을 교정해줄 언어모델 prior 가 없다 —
`홍길둥` 은 `홍길동` 으로 교정되지만 숫자는 안 된다. 9B 급 모델에서 신뢰할 수
없고, 이건 모델 크기 문제가 아니라 원리 문제다. 그래서 긴 숫자열 전사는 오히려
PaddleOCR 의 rec 이 더 정확하다 (문자 시퀀스 인식 전용으로 학습됐다).

①②만 있으면 이렇게 된다.

```
VLM:  "901231-1234561"   (실제로는 마지막 자리 오독)
OCR:  "901231-1234563"   (정확)
  → 완전일치 실패 → 좌표 포기 (vlm_coarse)
```

**잘하는 일(위치 판단)의 결과를 못하는 일(숫자 전사)이 가로막는다.** 정작 OCR 은
정답을 읽었는데 쓰지 못한다. 스스로 세운 원칙("VLM=의미, OCR=문자")을 매칭
단계에서 어긴 것이었다.

③을 넣으면 위 케이스가 이렇게 끝난다 — 좌표는 OCR 것으로 확정되고, 최종 `text`
도 OCR 것이 되므로 **체크섬이 통과한다.** VLM 오독으로 체크섬이 깨지던 문제가
같이 사라진다.

```
source=ocr_refined   bbox=(358,426,442,454)   checksum=ok   verified=True
agreement=none       needs_review=True
reason="VLM bbox 와 위치가 겹치는 OCR 박스를 선택 (텍스트는 불일치).
        VLM '901231-1234561' vs OCR '901231-1234563'; 체크섬 통과"
```

③은 `FAILED` 박스도 후보에 넣는다. det 는 성공하고 rec 만 실패한 박스는 "여기
글자는 있는데 못 읽었다" 는 뜻이고, VLM 이 그 자리를 지목했다면 **그 좌표가
VLM 근사치보다 정확하다.** 손글씨 칸이 여기서 `vlm_coarse` 를 벗어난다 —
텍스트 매칭으로는 원리적으로 불가능했던 회수다.

그럼 왜 VLM 에게 `text` 를 계속 요구하는가. 다운스트림이 필요해서가 아니다.
**모델이 픽셀을 실제로 보게 만드는 장치다.** "여기 개인정보 있냐" 만 물으면
모델은 레이아웃 prior 로 답할 수 있다 — "이 서식의 이 위치는 보통 주민번호
칸이니까". 칸이 비어 있어도 그렇게 답한다. 값을 적게 하면 그게 안 된다.
뭔가를 적으려면 봐야 한다. 그래서 `text` 의 역할이 **필수 조건에서 확인 증거로**
강등된 것이고, 사라진 것이 아니다.

**③의 대가는 정직하게 적어 둔다.** VLM bbox 가 어긋나면 엉뚱한 셀이 조용히
선택된다. ①②에는 없던 실패 모드다 (그건 못 찾으면 못 찾았다고 했다).
완충 장치는 셋이다.

- 가장 좁은 후보를 우선한다 (중심 포함 → 면적 커버 → 최대 겹침 순)
- `max_join` 이 과선택 상한이다. 넉넉한 bbox 가 옆 칸까지 덮었을 때 무한정
  딸려오지 않게 막고, 자를 때는 VLM 이 지목한 중심에 가까운 것을 남긴다
- `agreement=none` + `needs_review` + `reason` 에 양쪽 판독을 함께 남긴다

`locate.geometry_fallback: false` 로 끄면 이전 동작으로 돌아간다. A/B 로 실측해
③이 정말 값을 하는지(그리고 과선택이 얼마나 생기는지) 확인할 수 있게 남겨 뒀다.

### 4-1-1. 크롭에서 인정한 공차를 선택에서도 인정한다

③에는 실제로 파이프라인을 통째로 무력화한 버그가 있었다. **크롭은 VLM 좌표가
어긋난다는 전제로 35% 넉넉히 뜨는데, 박스 선택은 어긋나지 않았다는 전제로
패딩 없는 VLM bbox 와의 겹침만 봤다.**

밀림이 bbox 크기를 넘으면 세 후보 단계가 모두 빈손이 되고 `select_by_geometry` 가
`None` 을 돌려준다. 그러면 항목은 `vlm_coarse` 로 떨어져 **VLM 원본 좌표가 그대로
최종 좌표가 된다.** grounding 이 전반적으로 밀린 페이지에서는 이것이 항목 하나가
아니라 **전부**에 일어난다 — 오버레이가 전부 빨강이 되고, 화면에는 "VLM 이 좌표를
못 잡는다" 로 보인다. 실제로는 좌표를 교정하려고 만든 단계가 좌표가 부정확할 때
정확히 작동을 멈춘 것이다. 자기 전제를 부정하는 설계였다.

그래서 4단계를 넣었다 — 겹치는 박스가 하나도 없으면 **크롭 사각형 안에서** VLM
중심에 가장 가까운 줄을 고른다. 탐색 범위가 크롭으로 닫혀 있으므로 페이지
전체로 번지지 않는다. 그리고 이때는 **OCR 박스와 VLM 좌표를 함께 덮는다.**
어느 쪽이 맞는지 알 수 없는 상황에서 한쪽만 택하면 틀렸을 때 값이 안 가려진
채 남기 때문이다. 덧칠은 미탐보다 싸다.

같은 방향으로 하나 더 바꿨다. 텍스트 매칭이 실패했을 때 기하 선택은 이제
**넓은 크롭**의 박스를 쓴다. "좁은 크롭이 옆 칸을 덜 물어온다" 는 이점은 VLM
좌표가 정확할 때만 성립하는데, 텍스트 매칭까지 실패했다는 것 자체가 그 전제가
깨졌다는 신호다. 좁은 크롭을 지키면 어긋난 자리만 계속 들여다본다.

남은 `vlm_coarse` 는 이제 **크롭에 박스가 하나도 없는 경우**뿐이다. 그래서 이
건수는 이제 순수하게 OCR 검출 신호로 읽을 수 있다 — 예전에는 VLM 좌표 문제와
섞여 있어 구분이 안 됐다. 밀린 건은 `근접 선택` 으로 따로 집계되고 경고에도
따로 나온다.

### 4-2. 유사 매칭 단계는 제거했다

한때 ②와 ③ 사이에 "글자가 비슷하면 같은 값으로 본다" 는 단계가 있었다
(`SequenceMatcher` 임계값 0.65, `NAME`/`ADDRESS`/`ORG`/`TITLE` 에만 적용).
지웠다.

**③이 같은 일을 더 안전하게 하기 때문이다.** 텍스트가 비슷하면서 위치도 겹치면
③이 같은 박스를 고른다. 위치가 안 겹치면 애초에 다른 값이므로 유사도로
이어붙여선 안 된다 — 특히 숫자는 한 글자 다르면 "오독된 같은 번호" 가 아니라
**그냥 다른 사람의 번호**이고, 옆 칸에 붙으면 엉뚱한 사람을 마스킹하면서 정작
그 사람은 놓친다.

유사 매칭이 있던 시절에는 임계값 하나(0.65)와 라벨 분류 하나
(`SIMILARITY_LABELS`)와 최소 길이 하나(`_SIM_MIN_LEN`)를 함께 튜닝해야 했다.
셋 다 없어졌고, 잃은 기능은 없다. `Agreement.SIMILAR` 도 같이 사라졌다.

### 4-3. 다중 샘플 합집합 — 학습 없이 미탐을 줄이는 손잡이

`detect.samples` 를 2 이상으로 두면 같은 타일을 여러 번 뽑고 `_dedup` 이
합집합을 만든다. 한 번은 놓치고 다른 번엔 잡히는 항목이 회수된다.

**재현율이 오르고 정밀도가 떨어진다.** 마스킹에서 이 거래는 대체로 맞다 —
미탐은 개인정보가 마스킹 없이 나가는 것이고, 과탐은 멀쩡한 칸을 덧칠하는
것이다. 비용이 같은 급이 아니다.

대가는 호출 수다: `tiles × samples`. 타일 호출은 서로 독립이라 병렬로 나가므로
(`detect.workers`) 벽시계 시간은 호출 수만큼 늘지는 않는다.

`samples == 1` 이면 온도를 건드리지 않는다. 기본 동작은 결정론이어야 한다 —
같은 문서를 두 번 돌렸을 때 결과가 다르면 감사 대응이 불가능하다.

값은 실측으로 정할 것. `scripts/measure.py` 가 1 회와 3 회를 같은 문서에서
비교해준다.

### 4-3. 좌표가 밀렸을 때의 진단 — `scripts/diagnose.py`

"박스가 밀렸다" 는 관찰은 서로 처방이 다른 다섯 원인 중 하나이고, 눈으로는
구분되지 않는다. 좌표 규약 오류 / 배율 어긋남 / 체계적 평행이동 / 무작위
grounding 오차 / 크롭 OCR 실패. 잘못 짚으면 아무 문제 없는 코드를 고친다.

두 수치가 이것을 가른다. **중앙 오프셋**은 VLM bbox 중심에서 확정된 OCR 박스
중심까지의 벡터고, **최적 배율**은 `ocr ≈ k·vlm + b` 의 최소제곱 기울기다.
절편 `b` 를 함께 추정하는 것이 핵심이다 — 원점을 지나는 직선으로 맞추면 순수한
평행이동도 기울기로 흡수되어 (0.05 만 밀려도 `k≈1.08`) 배율 오차로 오진한다.
절편을 두면 기울기는 배율만, 중앙 오프셋은 평행이동만 본다. 그리고 기울기
이탈은 **표준오차보다 뚜렷할 때만** 배율 문제로 부른다.

이 진단기는 **문서 내용을 출력하지 않는다.** 값·필드명·파일명·OCR 텍스트를
찍지 않고 건수·비율·기하 통계·판정 문구만 낸다. 폐쇄망에서 화면을 그대로 읽어
나와야 하는 상황을 전제로 만들었고, 그 성질은 성능이 아니라 **계약**이므로
`tests/test_diagnose.py::TestNoLeak` 이 값을 심어 놓고 출력에 없음을 검증한다.

집계에 `vlm_coarse` 를 넣지 않는다는 점이 미묘하지만 중요하다. 그쪽은 최종
좌표가 VLM 것이라 오차가 정의상 0 이고, 넣으면 밀림이 있는데도 0 으로 희석되어
판정이 "문제 없음" 으로 뒤집힌다. `nearby` 건도 `bbox` 가 VLM 좌표까지 덮고
있으므로 `member_index` 가 가리키는 OCR 박스만 본다.

### 5. 규칙은 탐지기가 아니라 검증기다

같은 지식(자리수·체크섬)이 **탐지기**로 쓰였던 것이 이전 구조 최악의 오류를
만들었다.

```
정규식이 탐지기였을 때:
  12자리 숫자열 → "체크섬 통과한 운전면허번호, confidence 1.00, 검토 불필요"
  · DRIVER_LICENSE 는 VALIDATORS 에 없어서 checksum_ok 초기값 True 가 그대로 남았다
  · 그 결과 문맥 키워드 검사(`not checksum_ok` 안에 있었다)도 건너뛰었다
  · 하이픈을 흘린 주민등록번호(13→12자리)가 여기로 빨려 들어가 확정 라벨을 받고
    <CONFIRMED:DRIVER_LICENSE> 태그로 두 LLM pass 에서 제외됐다
  → OCR 숫자 하나 손실이 주민등록번호를 영구히 세탁했다

체크섬이 검증기일 때:
  VLM: "RRN: 901112-2846261"
    → 자리수를 센다 (13 ✓)  → 체크섬을 돈다 (통과 → verified)
  VLM: "DRIVER_LICENSE: 901231-1234563"
    → 13자리인데 면허번호는 12자리다 → 경고 + type 교정
```

**검증기는 틀린 답을 만들 수 없다.** 최악의 경우 "모르겠다" 를 낼 뿐이다.
탐지기였을 때는 틀린 답을 확신을 담아 만들어냈다.

자리수·구성 형식 지식은 프롬프트의 형식표로 옮겼다. 정규식은 "13자리 6-7" 과
"12자리 2-2-6-2" 를 구분할 근거가 없어 우선순위 정렬에 의존했고 그게 역전됐다.
모델은 표를 보면 센다.

검증에는 **두 엔진의 값을 모두 시도**한다. OCR 이 한 자리 흘렸어도 VLM 이
온전하면 값은 실재하고, 그 반대도 마찬가지다.

`type` 교정은 **주민등록번호 체크섬 통과에만** 허용한다. 13자리 + 가중치 검증을
우연히 통과하기는 어렵다. 사업자·법인번호 체크섬은 자리수가 짧아 우연 통과
확률이 높으므로 교정 근거로 쓰지 않는다. `RRN`/`FOREIGN_ID`/`CORP_NO` 사이의
혼동도 교정하지 않는다 — 셋 다 마스킹 대상이라 경미하다. **13 ↔ 12자리 혼동만
고친다.** 그게 실제로 관측된 위험한 오류다.

### `source` — "출처" 가 아니라 **좌표 획득 경로**

탐지 판단은 전부 VLM 이므로 출처를 구분할 의미가 없다. 다운스트림이 알아야 하는
것은 **좌표를 믿어도 되는가**다.

| source | 의미 | 권장 처리 |
|---|---|---|
| `ocr_refined` | 크롭 OCR 이 좌표를 확정. 픽셀 단위로 정확 | 자동 처리 |
| `vlm_coarse` | VLM 좌표 근사. 부정확 | 검토 필수 (서명·인영은 예외) |

판단 근거는 별도 필드로 분리했다.

| 필드 | 뜻 |
|---|---|
| `agreement` | `exact` / `none` — 두 엔진의 값 교차검증 결과 |
| `verified` / `checksum` | 체크섬 통과 여부. `checksum: null` 은 "그 라벨에 체크섬이 없다" 이고 `"failed"` 와 구분된다 |
| `text` / `vlm_text` | 각각 OCR 이 읽은 값과 VLM 이 읽은 값. **둘 다 남긴다** |

`text` 와 `vlm_text` 를 모두 남기는 것이 이 재설계에서 얻은 가장 실용적인
자산이다. 어긋났을 때 **어느 엔진을 손봐야 하는지 로그만 보고 알 수 있다.**
이전 구조에서는 이 정보가 그냥 사라졌다.

### 무음 실패를 만들지 않는다

이 파이프라인에서 가장 위험한 결과는 "개인정보 없음" 처럼 보이는 실패다.
세 곳에서 막는다.

1. **좌표를 못 잡아도 항목을 버리지 않는다.** `findings` 와 `regions` 는 항상
   1:1 이다. 못 잡은 것은 `vlm_coarse` 로 남고 `reason` 에 왜 못 잡았는지 적힌다.
2. **빈 결과의 원인을 구분한다.** guided decoding 은 형식만 보장하므로, 과부하
   상태의 모델이 내는 가장 싼 스키마 적합 응답이 빈 배열이다. VLM 호출이
   실패해서 비었으면 `"개인정보 없음이 아님"` 이라고 경고에 명시한다.
3. **형식 이탈을 경고로 올린다.** `salvage_json` 이 복구에 성공해도 경고를
   남긴다 — 프롬프트가 예산을 넘겼다는 신호다.

`char_span` 은 `text` 내 문자 오프셋이다. 부분 마스킹(`901231-1******`)을
구현할 다운스트림이 쓴다. 단 `bbox` 는 항상 **박스 전체 영역**임에 유의 —
OCR 이 문자 단위 좌표를 주지 않으므로 글자수 비례 분할은 근사치다.
같은 박스에 두 종류가 섞여 있으면 영역이 두 개 나오므로, 부분 마스킹을
구현할 때 **박스의 모든 영역을 함께 적용**해야 한다.

라벨 18종의 목록과 검증 방식은 [`../README.md`](../README.md) 8번 절에 있다.

## 예상 지연시간

A4 1장, A100 80GB, Qwen3.5-9B bf16, 타일 3개 기준:

| 단계 | 시간 |
|---|---|
| 전처리 | 0.2~0.5s |
| VLM 탐지 (타일 3 × 이미지 ~1.5k tok + 출력 ~700tok) | 3~5s |
| 크롭 OCR (크롭 ~25개, 배치 2회) | 1~2.5s |
| 검증·정리 | <0.05s |
| **합계** | **약 5~8초** |

이전 구조와 비슷하다. LLM 호출이 2회에서 3회로 늘었지만 **프롬프트가 짧아지고
prefix caching 이 걸리며**, OCR 이 페이지 전체가 아니라 크롭에만 돌기 때문이다.

타일 수를 늘리면 탐지 시간이 거의 선형으로 늘어난다. `n_findings` 를 보고
필요한 만큼만 쓸 것 — 조각당 10건 내외가 기준이다.

## 확장 포인트

### 정형 식별자 추가

1. `schema.py` 의 `PII_LABELS` 에 라벨 추가
2. `llm/prompts.py` 의 `_FORMATS` 에 자리수·구성 한 줄
3. 체크섬이 있으면 `rules/checksums.py` 의 `VALIDATORS` 에
4. 자리수 검사를 원하면 `verify.py` 의 `DIGIT_LENGTHS` 에

`tests/test_schema.py` 가 1과 2의 불일치를 잡아준다. **패턴을 추가할 곳은
없다** — 정규식 탐지 레이어를 제거했다.

### 과검 줄이기

운영 단계에서 범위를 좁힐 곳은 두 군데다.

- `llm/prompts.py` 의 `_INCLUSIONS` — 기관 정보·문서 날짜·식별번호를 빼려면 여기
- `verify.py` 의 `FIELD_LABEL_WORDS` — 서식별 헤더 문구 추가

탐지 자체가 프롬프트에서 나오므로, 후단 필터를 새로 만들기보다 프롬프트를
좁히는 편이 낫다. 후단 필터는 왜 걸러졌는지가 로그에만 남는다.

### 검증 방법

`scripts/make_synthetic.py` 는 **정답 JSON 을 함께 출력**한다. 의도적으로
손글씨/도장/저대비/다단 컬럼/인라인 라벨을 섞어두었으므로 난이도별 recall 을
분리해 측정할 수 있다 (`difficulty` 필드).

**아직 평가 스크립트가 없다.** 정답 JSON 과 결과 JSON 을 대조해
`n_findings` 기준 recall 과 `localized_rate` 를 뽑는 `scripts/eval.py` 가
다음 작업이다. 그게 없으면 계속 `boxes.png` 를 눈으로 보며 프롬프트를 만지게 된다.

시각화 검수는 `{이름}.boxes.png` 가 가장 빠르다. 색이 두 개뿐인 것은 의도한
것이다 — 검수자가 내릴 판단이 "좌표를 믿어도 되나" 하나이기 때문이다.
체크섬 결과는 라벨 접미사(`OK`/`X`)로 붙는다.

진단할 때는 `--include-ocr` 를 켠다. `findings`(VLM 원본)와 `ocr_boxes`(크롭 OCR
결과)를 나란히 볼 수 있어야 어느 단계를 손볼지 판단할 수 있다.

## 좌표계 주의

결과 좌표는 **전처리된 이미지 기준**이다. 원본 좌표계로 되돌려야 하면
`PreprocessResult.transform`(scale / rotation_deg / rotation_center)으로 역변환한다.
기울기 보정은 각도가 0.4°~15° 구간일 때만 적용된다.

크롭도 전처리된 이미지에서 뜬다. 원본 스캔이 `target_long_side` 보다 크면
`target_long_side: null` 로 두는 편이 크롭 OCR 에 유리하다 — 다만 VLM 입력이
커지므로 `detect.tiles` 를 함께 늘려야 한다.
